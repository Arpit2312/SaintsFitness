# Phase 7: Settings & Notifications — Design Spec

## Goals & Scope

Phase 7 finishes the roadmap ("Settings & polish"). Per the original brief it
delivers:

1. **Settings** — Academy Settings (name, logo, address, mobile, email),
   Receipt Settings (prefix, number format, footer message) and Fee Reminder
   Settings (message template, due-soon days, overdue reminder frequency),
   plus the existing password change — wired into the real receipts, receipt
   numbers and reminder messages, not just stored.
2. **Notification center** — a bell with an unread count in the header and a
   `/notifications` page for five event types: fee overdue, fee due soon, low
   attendance, new admission, payment received. Mark read / mark all read.
3. **Dashboard "Recent Activity"** — the latest ~10 events (payments, new
   students, batch joins, fee reminders sent, attendance), derived from
   existing tables with no new tracking table.

**Decisions taken with the user:** full brief in scope; time-based
notifications are created by events plus a throttled sync on load (no
scheduler, no cron secret); the logo is an `https://` URL field (there is no
file-storage service in the app).

**Out of scope:** per-user notification preferences, email/SMS/push delivery,
file upload for the logo, notification pruning, roles beyond Admin, editing
existing receipts.

## Data Model (additive migration only)

- **New model `AcademySettings`** — a singleton: a fixed `id` of `"default"`,
  written with upsert; when no row exists the code uses the defaults below.
  Fields (all with defaults or nullable):
  - Academy: `academyName String` (default `"SAINTS"`), `logoUrl String?`,
    `address String?`, `mobile String?`, `email String?`.
  - Receipt: `receiptPrefix String` (default `"SNT"`),
    `receiptIncludeYear Boolean` (default `true`), `receiptFooter String`
    (default `"Thank You"`).
  - Fee reminder: `reminderTemplate String` (default = today's exact wording,
    see below), `dueSoonDays Int` (default `3`), `overdueReminderDays Int`
    (default `7`).
  - `lastNotificationSyncAt DateTime?`, `updatedAt DateTime @updatedAt`.
- **`Notification`** gains `dedupeKey String? @unique` (and an index on
  `read`). `type` stays a `String`; valid values are `FEE_OVERDUE`,
  `FEE_DUE_SOON`, `LOW_ATTENDANCE`, `NEW_ADMISSION`, `PAYMENT_RECEIVED`.

## What Each Setting Does

- **Academy:** name, logo, address, mobile and email appear on the receipt;
  name and logo appear in the sidebar; the name feeds `{academy}` in reminder
  messages. Logo must be an `https://` URL (rendered with a plain `<img>`).
- **Receipt:** the number is `{prefix}-{year}-{sequence:5}` (e.g.
  `SNT-2026-00045`) when "include year" is on, else `{prefix}-{sequence:5}`.
  The prefix is 2–8 uppercase letters/digits only (no hyphens) so no two
  configurations can ever produce the same string (`Receipt.receiptNumber`
  is unique). The counter is the existing `Sequence` table: named
  `receipt-<year>` when the year is included, `receipt-all` when it is not
  (a year-less number must not restart every January). The footer replaces
  the hard-coded "Thank You" on the receipt page and in the WhatsApp share
  text. Changing settings never rewrites an existing receipt.
- **Fee reminder:** the template supports the placeholders `{name}`,
  `{amount}` and `{academy}`. The default template reproduces the current
  message exactly:
  `SAINTS – Fee Reminder` / `Hi {name}, this is a reminder that ₹{amount} is
  pending for your SAINTS fees. Please clear it at your earliest
  convenience. Thank you!` — the default is that literal text (containing
  only `{name}` and `{amount}`), so the default output does not depend on the
  academy name and the existing message tests keep passing unchanged;
  `{academy}` is available for admins who write a custom template.
  `sendFeeReminder` renders it
  server-side and returns it, preserving the Phase 4 guarantee that the
  logged message and the sent message can never drift. "Due soon days" sets
  how early a fee-due-soon notification fires. "Overdue reminder frequency"
  is how often (in days) a still-overdue student is re-notified.

## Notifications

- **Event-driven:**
  - `NEW_ADMISSION` is created in `createStudent` ("Priya Singh joined
    SAINTS."), dedupe key `admission:<studentId>`.
  - `PAYMENT_RECEIVED` is created in `createPayment` ("Rahul Sharma paid
    ₹1,500 via UPI."), dedupe key `payment:<paymentId>`.
  - A failure to write a notification is caught and logged; it never fails
    the admission or the payment.
- **Time-based, generated by a throttled sync** (`syncTimeBasedNotifications`):
  - `FEE_OVERDUE`: a student with any past-due unpaid balance (Phase 5's
    `classifyDues` "OVERDUE" definition). Dedupe key
    `overdue:<studentId>:<cycle>` where `cycle =
    floor(daysSinceEpoch(todayInIST) / overdueReminderDays)` — at most one
    per student per frequency window while they remain overdue.
  - `FEE_DUE_SOON`: a pending student who is not overdue and whose next
    unpaid period's due date is within `dueSoonDays` of today. Dedupe key
    `duesoon:<studentId>:<dueDate as YYYY-MM-DD>` — once per due date.
    `listPendingStudentsWithDues` (Phase 5) additionally returns
    `nextDueDate`, the earliest due date among periods that still have an
    unpaid balance and are not yet past due (`null` if none).
  - `LOW_ATTENDANCE`: an active student with at least 5 marked classes in
    the last 30 days and an attendance rate below 60%. Dedupe key
    `lowatt:<studentId>:<YYYY-MM>` — at most once per calendar month. The
    thresholds (5 classes, 30 days, 60%) are constants in code; the brief
    lists no setting for them.
- **Sync throttle and concurrency:** the `(app)` layout calls the sync
  before counting unread notifications. The sync runs only if
  `lastNotificationSyncAt` is null or older than 30 minutes. It first
  *claims* the run with an atomic conditional `updateMany` on that
  timestamp (only the caller whose update affects one row proceeds), then
  inserts candidates with `createMany({ skipDuplicates: true })` against the
  unique `dedupeKey`. A sync failure is caught and logged and never breaks
  page rendering.
- **Notification center:** `/notifications` lists the latest 100
  (newest first; unread visually distinct), each with its message, a
  date, a link to the student profile when `studentId` is set, and "Mark
  read"; plus "Mark all read". The header bell shows the unread count
  (one indexed count query per page load) and links to `/notifications`.
  Actions: `markNotificationRead(id)`, `markAllNotificationsRead()`.

## Recent Activity

Derived on read (no new table) by taking the latest rows of each source,
mapping them to `{ at, text }` events, and merging by time (newest first,
capped at 10) with the pure function `mergeActivity`:

- Payments (by `createdAt`): "Rahul Sharma paid ₹1,500 via UPI."
- New students (by `createdAt`): "Priya Singh joined SAINTS."
- Batch joins (`Enrollment.joiningBatchDate`): "Priya Singh joined Morning
  Zumba."
- Fee reminders (`sentAt`): "Fee reminder sent to Rahul Sharma."
- Attendance, **summarized per batch and date** so one roll call is one
  event: "Morning Zumba attendance marked: 12 of 15 present." (Fetch the
  latest 60 attendance rows by `createdAt`, group by batch + date.)

All sources exclude soft-deleted students. It renders as a card on the
dashboard below the stat cards.

## Architecture

- **Migration:** `AcademySettings` model, `Notification.dedupeKey` (unique)
  and an index on `Notification.read`.
- **Pure, unit-tested modules:**
  - `src/lib/settings/defaults.ts` — `DEFAULT_SETTINGS`, `SettingsValues`.
  - `src/lib/settings/receipt.ts` — `formatReceiptNumber({ prefix,
    includeYear, year, sequence })`, `receiptSequenceName(includeYear,
    year)`.
  - `src/lib/settings/reminder-template.ts` — `renderReminderTemplate(
    template, { name, amount, academy })` and `DEFAULT_REMINDER_TEMPLATE`.
    `buildReminderMessage` (Phase 4) gains an optional `{ template,
    academyName }` argument; its default output stays byte-identical.
  - `src/lib/validations/settings.ts` — three zod schemas: academy (name
    2–60; mobile optional 10-digit `^[6-9]\d{9}$`; email optional valid;
    logo optional `https://` URL; address ≤ 300), receipt (prefix
    `^[A-Z0-9]{2,8}$` uppercased on input; include-year boolean; footer ≤
    200), reminder (template 10–500 chars containing `{name}` and
    `{amount}`, and only the three known placeholders; `dueSoonDays` int
    1–30; `overdueReminderDays` int 1–60). Empty optional strings normalize
    to `null`.
  - `src/lib/notifications/candidates.ts` — pure builders returning
    `{ type, studentId, message, dedupeKey }` for overdue / due-soon /
    low-attendance, plus `overdueCycle(today, days)`, and
    `isSyncStale(lastSyncAt, now)`.
  - `src/lib/notifications/activity.ts` — `mergeActivity`.
- **Server layer:**
  - `src/lib/queries/settings.ts` — `getSettings()` (defaults when no row).
  - `src/actions/settings.ts` — `saveAcademySettings`,
    `saveReceiptSettings`, `saveReminderSettings` (each validates then
    upserts the singleton, then revalidates the affected paths).
  - `src/lib/queries/notifications.ts` — `listNotifications`,
    `countUnreadNotifications`; `src/actions/notifications.ts` — the two
    mark-read actions; `src/lib/notifications/create.ts` — a safe
    `createNotification` helper (catch + log) used by the event-driven
    hooks; `src/lib/notifications/sync.ts` (server-only) — the throttled
    claim-then-insert sync; `src/lib/queries/activity.ts` —
    `getRecentActivity()`.
  - Modified: `src/lib/ids.ts` (`generateReceiptNumber` reads the prefix
    and include-year settings), `src/actions/students.ts`
    (`createStudent` notification), `src/actions/fees.ts` (`createPayment`
    notification), `src/actions/reminders.ts` (`sendFeeReminder` renders
    the template), `src/lib/queries/reports-dues.ts` (`nextDueDate`),
    `src/app/receipts/[paymentId]/page.tsx` (academy header, logo, contact
    lines, footer, share text), `src/app/(app)/layout.tsx` (sync + unread
    count + settings for the sidebar), `src/components/layout/header.tsx`
    (bell), `src/components/layout/sidebar.tsx` (academy name/logo),
    `src/app/(app)/dashboard/page.tsx` (Recent Activity),
    `src/app/(app)/settings/page.tsx`.
- **UI (new):** settings forms for Academy, Receipt and Fee Reminders (each
  its own card, form and Save; the reminder form shows a live preview of the
  rendered message using the pure renderer), `notification-bell.tsx`, the
  `/notifications` page and list, and a `recent-activity.tsx` card.
  Forms use plain controlled state (no `react-hook-form`), no
  `useEffect`+`setState` reseeding, and Title Case labels, per the lessons
  of earlier phases.

## Error Handling & Edge Cases

- A missing settings row uses defaults; empty optional fields are stored as
  `null`; validation errors are shown inline; a failed save shows the
  generic error toast.
- Changing the prefix or year toggle affects only future receipts.
- The sync and event-driven notification writes never break the page or the
  underlying admission/payment.
- Notification, sync and activity queries exclude soft-deleted students.
- "Mark all read" only touches unread rows. The unread count and list are
  simple queries bounded by the index and the 100-row cap.
- Everything is admin-only, exactly as protected as the existing actions.
- Logo `https://` restriction prevents `javascript:`/`data:` URLs in `src`.

## Testing Strategy

Pure-logic unit tests (project precedent): `formatReceiptNumber` and
`receiptSequenceName` (year/no-year, padding, prefix); `renderReminderTemplate`
(all placeholders, repeated placeholders, default template equals today's
exact message); the three settings schemas (each bound, normalization, prefix
casing, template rules, https-only logo); the candidate builders (overdue
cycle boundaries, due-soon window edges, low-attendance thresholds and
monthly key); `isSyncStale`; and `mergeActivity` (ordering, cap, grouping
input). Queries, actions, the sync and UI are verified manually against the
real database (no browser login is available in this environment), including
the sync's claim-and-dedupe behaviour under a simulated concurrent run.

## Post-Plan Check

At the end of this plan the roadmap is complete: the admin can configure the
academy, receipts and reminders; sees notifications for admissions, payments
and time-based fee/attendance conditions; and gets a live activity feed on the
dashboard.
